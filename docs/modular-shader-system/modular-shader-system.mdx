Poiyomi Shaders is put together using the Modular Shader System, which allows for modular architecture on each individual features. This is a comprehensive guide to creating shader modules for the Poiyomi Shaders framework.

:::warning[Complex Information Ahead!]
This page contains complex information! Therefore, this is intended to be read by Advanced Shader Developers only.
:::

## Quick Start

The fastest way to make a module is `Poi -> Create New Module`. Name it, pick where its settings appear and where its code runs, then click `Create`. You get a folder containing the two files described below.

Then open any Poiyomi material, expand `Third Party`, and click `Install` on your module. That material's shader rebuilds and your settings appear in its inspector. The shader's name doesn't change. Other Poiyomi shaders pick the module up the first time you select a material that uses them. To take it out again, use `Remove` in the <FAIcon icon="fa-solid fa-ellipsis-vertical"/> menu on your module's section.

The rest of this page explains what the Wizard sets up for you. For how installing, updating and removing works from the user's side, see [Third Party](/third-party/third-party.mdx).

## Overview

The Poiyomi Shader system uses a modular architecture where individual features are defined as separate modules. Each module consists of two main files:

1. **Module Definition** (`.asset`) - YAML file defining module metadata and template references
2. **Template Collection** (`.poiTemplateCollection`) - Contains the actual shader code templates

The template collection is a plain text file. On import, every `#T#` section in it becomes its own sub-asset, named after its header. The module definition then points each section at one or more [injection keywords](#common-keywords-injection-points).

:::tip
Don't hand-edit the `fileID` references in the `.asset` file. Create the module with the wizard, or assign templates in the module's inspector, and let Unity write them.
:::

## File Structure

```
Poi_FeatureModules/
├── Poi_YourModule/
│   ├── VRLM_PoiYourModule.asset           # Module definition
│   ├── VRLM_PoiYourModule.asset.meta
│   ├── VRLTC_PoiYourModule.poiTemplateCollection  # Shader code
│   └── VRLTC_PoiYourModule.poiTemplateCollection.meta
```

Poiyomi's own modules live in `Poi_FeatureModules/`. A Third Party module can live anywhere in the project, as long as it's **outside** the Poiyomi folder. See [What is a Third Party Module](/third-party/third-party.mdx#what-is-a-third-party-module) for why.

### Naming Convention

| Prefix | Type |
|--------|------|
| `VRLM_` | Module Definition (asset) |
| `VRLT_` | Single Template (poiTemplate) |
| `VRLTC_` | Template Collection (poiTemplateCollection) |

### Key Fields

| Field | Description |
|-------|-------------|
| `Id` | Unique identifier for the module. Must be unique across the whole project, since dependencies and conflicts use it |
| `Name`, `Version`, `Author`, `Description` | Shown on the module's row in Third Party before it's installed. Bump `Version` with each release, so the **Update** button can show which version people are moving to |
| `Icon` | Optional texture shown at the start of that row. Without one, a puzzle piece is shown |
| `ModuleDependencies` | Ids of modules that must also be installed |
| `IncompatibleWith` | Ids of modules that can't be installed alongside this one |
| `AllowDuplicates` | Whether the same module can appear more than once. See [Duplicate Module Support](#duplicate-module-support) |
| `Templates` | References to template sections with keyword mappings |
| `Queue` | Set on each template entry. Priority order (lower = earlier in shader). See [Ordering](#ordering) |

Dependencies and conflicts are checked before install. A module with an unmet dependency can't be installed, and its row in Third Party shows why.

## Template Collection (.poiTemplateCollection)

Templates contain shader code organized into named sections. Each section is marked with `#T#SectionName`.

### Template Structure

```hlsl
#T#YourModuleProperties
//ifex _EnableYourModule==0
[HideInInspector] m_start_yourModule (" Your Module--{reference_property:_EnableYourModule}", Float) = 0
[HideInInspector][ThryToggle(POI_YOUR_MODULE)]_EnableYourModule ("Enable", Float) = 0
_YourProperty ("Property Name", Range(0, 1)) = 0.5
[HideInInspector] m_end_yourModule ("", Float) = 0
//endex

#T#YourModuleKeywords
//ifex _EnableYourModule==0
#pragma shader_feature_local POI_YOUR_MODULE
//endex

#T#YourModuleVariables
//ifex _EnableYourModule==0
#ifdef POI_YOUR_MODULE
    float _YourProperty;
#endif
//endex

#T#YourModuleFunction
//ifex _EnableYourModule==0
#ifdef POI_YOUR_MODULE
    void ApplyYourModule(inout PoiFragData poiFragData, in PoiMesh poiMesh)
    {
        // Your shader logic here
    }
#endif
//endex

#T#YourModuleFunctionCall
//ifex _EnableYourModule==0
#ifdef POI_YOUR_MODULE
    ApplyYourModule(poiFragData, poiMesh);
#endif
//endex
```

## Common Keywords (Injection Points)

Keywords define where code is injected into the shader pipeline. Keywords are marked with `#K#` in templates. For example, `#K#FRAGMENT_BASE_COLOR` in a pass program is where everything targeting `FRAGMENT_BASE_COLOR` gets pasted.

Keywords are per pass. `BASE` is the main forward pass. The others are `ADD` (extra realtime lights), `META` (lightmap baking), `SHADOW` (shadow caster), `OUTLINE`, `LILFUR` (fur), `DEPTH` (depth only and depth normals), and `MOTION_VECTORS` (URP only). Two-pass and grab pass shaders also have `BASETWO`/`ADDTWO` and `SELF_GRAB` versions of some keywords, listed in the tables below. Target every pass you want your effect to appear in.

Targeting a keyword that a pass doesn't have is harmless. Injection is a plain text match, so that template is skipped silently instead of causing an error. The flip side is that a misspelled keyword doesn't cause an error either; that code just never shows up in the shader.

### The Four Keywords a Typical Module Needs

| Section | Keyword | Holds |
|---------|---------|-------|
| Properties | One [UI section](#property-categories) | Shader properties, which make up the inspector UI |
| Variables | `<PASS>_PROPERTY_VARIABLES_EXPOSED` | Numeric declarations such as `float _MyThing;` |
| Functions | `FRAGMENT_<PASS>_FUNCTIONS` | Your function definitions |
| Function Calls | A [hook point](#fragment-execution-pipeline) | The call that runs your function |

### Top-Level Shader Structure

These keywords define the overall shader structure and pass ordering:

| Keyword | Description |
|---------|-------------|
| `SHADER_TAGS` | Shader-level tags and properties |
| `DEPTH_NORMALS_PASS` | Depth normals pass injection |
| `GRAB_PASS` | Grab pass for screen effects |
| `DEPTH_ONLY_PASS` | Depth only (early Z) pass |
| `EARLY_OUTLINE_PASS` | Early outline pass (before base) |
| `BASE_PASS` | Main forward base pass |
| `ADD_PASS` | Additive lighting pass |
| `SELF_GRAB_PASS` | Self grab pass |
| `BASE_PASS_TWO` | Second base pass (two-pass shaders) |
| `ADD_PASS_TWO` | Second additive pass |
| `OUTLINE_PASS` | Outline rendering pass. The lil Fur passes are injected here too |
| `SHADOW_PASS` | Shadow casting pass |
| `META_PASS` | Lightmapping/GI meta pass |
| `MOTION_VECTORS_PASS` | Motion vectors pass (URP only) |

### Fragment Execution Pipeline

These are the hook points where your code runs, in execution order within the fragment program. All of them sit in the same function body, so the same variables are in scope at every one.

| Keyword | Runs | Passes |
|---------|------|--------|
| `FRAGMENT_BASE_DECLARATIONS` | Structs are declared here. Don't target this | All |
| `FRAGMENT_BASE_INIT_EARLY` | Before mesh data is filled in | All |
| `FRAGMENT_BASE_INIT` | Mesh, light and camera data gets filled in | All |
| `FRAGMENT_BASE_INIT_LATE` | After setup, before any color | All |
| `FRAGMENT_BASE_COLOR_EARLY` | Before the main texture | All |
| `FRAGMENT_BASE_COLOR` | Main texture and decals. **The usual choice** | All |
| `FRAGMENT_BASE_COLOR_LATE` | After all color work | All |
| `FRAGMENT_BASE_LIGHTING_EARLY` | Before the lighting model | All except Depth, Motion Vectors and Self Grab |
| `FRAGMENT_BASE_LIGHTING` | Alongside the lighting model | All except Depth, Motion Vectors and Self Grab |
| `FRAGMENT_BASE_LIGHTING_LATE` | After the lighting model | All except Depth, Motion Vectors and Self Grab |
| `FRAGMENT_BASE_LIGHTING_ADD` | Adding light on top, such as rim lights and glows | Base, Add, Meta, Outline and LilFur |
| `FRAGMENT_BASE_EMISSION_EARLY` | Early emission | All except Depth, Motion Vectors and Self Grab |
| `FRAGMENT_BASE_EMISSION` | Main emission calculations | All except Depth, Motion Vectors and Self Grab |
| `FRAGMENT_BASE_EMISSION_LATE` | Late emission effects | All except Depth, Motion Vectors and Self Grab |
| `FRAGMENT_BASE_RETURN` | Last change before alpha cutout | All |
| `FRAGMENT_BASE_ALPHA_LATE` | After clipping | Base, Add, Outline, LilFur and Self Grab |

The same pattern applies to other passes: `FRAGMENT_ADD_*`, `FRAGMENT_OUTLINE_*`, `FRAGMENT_LILFUR_*`, etc. The **Passes** column shows which passes have each hook.

### Reflections & Specular Smoothness Modifiers

Code injected at `MOCHIE_METALLIC_SMOOTHNESS_MOD` should access the current Reflections & Specular instance through `POI_BRDF_MOD_DATA`, for example `POI_BRDF_MOD_DATA.smoothness`. The alias only exists around that hook, and it follows the current instance when Reflections & Specular is duplicated. Don't hardcode the first instance's `mochieBRDFData` identifier in injected modifiers.

## Ordering

Each template entry has a `Queue` (default `100`). Within a keyword, everything targeting it is sorted by `Queue` in ascending order, so lower runs earlier. There's no "run after module X" setting; it's one flat number.

Ties keep module order, and user modules are processed after Poiyomi's own. **So at the default `Queue` of 100, your code runs after Poiyomi's**, which is usually what you want.

These bands are used throughout the shader. They're a convention, not a rule:

| Queue | Used For |
|-------|----------|
| Negative | Before core setup |
| `0` | Core infrastructure, such as data structures and init |
| `1`–`99` | Features that must run before the bulk |
| `100` | Default. Most features |
| `101`–`999` | Features that must run after the bulk |
| `1000`+ | Last |

`Poi -> Tools -> Modular Shader -> Module Order Listing` lists every module targeting a given keyword, with editable queues.

## Core Data Structures

Five structs are declared before any hook point and filled in during `INIT`, so they're in scope at every fragment hook:

| Struct | Useful Fields |
|--------|---------------|
| `PoiFragData poiFragData` | `baseColor`, `finalColor`, `alpha`, `emission`, `smoothness`, `metallic` |
| `PoiMesh poiMesh` | `uv[11]`, `normals[2]`, `worldPos`, `localPos`, `vertexColor`, `isFrontFace`, `tangent[2]` |
| `PoiLight poiLight` | `finalLightAdd`, `direction`, `directColor`, `indirectColor`, `lightMap`, `nDotL`, `attenuation` |
| `PoiCam poiCam` | Camera position and vectors |
| `PoiMods poiMods` | `globalEmission` and other cross-module modifiers |

Note that `baseColor`, `finalColor` and `emission` are `half3`, not `half4`. Alpha is kept separately.

### PoiFragData

Fragment output data for color, lighting, and material properties.

```hlsl
struct PoiFragData {
    half3 baseColor;            // Albedo color before lighting
    half3 finalColor;           // Final color after all effects
    half alpha;                 // Transparency
    half3 emission;             // Emissive color
    
    // PBR Properties
    half smoothness;            // Primary smoothness (0-1)
    half smoothness2;           // Secondary smoothness for layered materials
    half metallic;              // Metallic value (0-1)
    half specularMask;          // Mask for specular highlights
    half reflectionMask;        // Mask for reflections
    
    half toggleVertexLights;    // Enable/disable vertex lights contribution
};
```

### PoiMesh

Mesh geometry, UVs, and vertex data.

```hlsl
struct PoiMesh {
    // Normals
    float3 normals[2];          // [0] = vertex normal, [1] = fragment/normal-mapped
    float3 objNormal;           // Object-space normal
    float3 tangentSpaceNormal;  // Normal in tangent space
    float3 binormal[2];         // Binormal vectors
    float3 tangent[2];          // Tangent vectors
    
    // Position
    float3 worldPos;            // World-space position
    float3 localPos;            // Object-space position
    float3 objectPosition;      // Object pivot position in world space
    
    // Face
    float isFrontFace;          // 1.0 = front face, 0.0 = back face
    
    // Vertex Data
    float4 vertexColor;         // Vertex color RGBA
    float4 lightmapUV;          // Lightmap UVs
    
    // UV Channels (11 total)
    // [0-3] = UV0-UV3
    // [4]   = Panosphere UV
    // [5]   = World position XZ
    // [6]   = Polar UV
    // [7]   = Distorted UV
    // [8]   = Local position
    // [9]   = Matcap UV
    // [10]  = Screen space UV
    float2 uv[11];
    
    // Parallax
    float2 parallaxUV;          // UV offset from parallax
    float2 dx;                  // Screen-space derivatives X
    float2 dy;                  // Screen-space derivatives Y
    
    uint isRightHand;           // Handedness for normal mapping
};
```

```hlsl
struct PoiCam {
```

### PoiLight

Lighting calculations and light source data.

```hlsl
struct PoiLight {
    // Light Direction & Color
    float3 direction;           // Light direction
    float3 directColor;         // Direct light color
    float3 indirectColor;       // Indirect/ambient light color
    float3 halfDir;             // Half vector (view + light)
    
    // Attenuation
    float attenuation;          // Light attenuation
    float attenuationStrength;  // Attenuation intensity
    float occlusion;            // Ambient occlusion
    float shadowMask;           // Shadow mask value
    float detailShadow;         // Detail shadow value
    
    // Dot Products
    float nDotL;                // Normal dot light direction
    float nDotV;                // Normal dot view direction
    float nDotH;                // Normal dot half vector
    float nDotVCentered;        // Centered nDotV
    float vertexNDotL;          // Vertex-based nDotL
    float vertexNDotV;          // Vertex-based nDotV
    float vertexNDotH;          // Vertex-based nDotH
    float lDotv;                // Light dot view
    float lDotH;                // Light dot half
    float nDotLSaturated;       // Clamped nDotL (0-1)
    float nDotLNormalized;      // Normalized nDotL (0-1 range)
    
    // Light Maps
    float lightMap;             // Light map value
    float lightMapNoAttenuation;// Light map without attenuation
    float3 rampedLightMap;      // Toon ramp applied light map
    
    // Final Lighting
    float3 finalLighting;       // Combined final lighting
    float3 finalLightAdd;       // Additive light contribution
    
    // LTCGI
    float3 LTCGISpecular;       // LTCGI specular contribution
    float3 LTCGIDiffuse;        // LTCGI diffuse contribution
    
    // Luminance
    float directLuminance;      // Direct light luminance
    float indirectLuminance;    // Indirect light luminance
    float finalLuminance;       // Final combined luminance
    
    // Add Pass Only
    #ifdef POI_PASS_ADD
    float additiveShadow;       // Shadow for additive pass
    #endif
    
    // Vertex Lights (4 non-important lights)
    #if defined(VERTEXLIGHT_ON)
```

## Duplicate Module Support

For modules that can have multiple instances (like Emission 0, 1, 2...):

```yaml

ForceDuplicateLogic: 1
```

Use placeholders in templates:
- `__mIDx__` - Replaced with instance index (0, 1, 2...)
- `__mID__` - Replaced with module ID string
- `<ms_include_in_first>{ }` - Only in first instance
- `<ms_include_in_not_first>{ }` - Only in subsequent instances
- `<ms_include_in_last>{ }` - Only in last instance

### Example: Multiple Backlight Instances

Custom modular shaders can include `PoiBacklight` more than once. For example, one instance with low Directivity and View Direction Strength for a front highlight, plus another for silhouette backlighting. The current default shaders include two independently enabled sections, **Backlight 1** and **Backlight 2**. Both are disabled by default, so existing materials look the same until the second one is turned on.

The generator keeps the first instance's existing property names and keyword. Additional instances use the standard `__1`, `__2`, etc. suffixes, for example `_BacklightDirectivity__1`, `_BacklightColorTex__1` and `POI_BACKLIGHT__1`. Colors, textures, directionality, shadow reception, backface masking and enable toggles are all independent. Each instance adds to `finalLightAdd` using the existing Backlight formula.

Global mask storage is shared on purpose. Mask writes and reads follow module order, so instances targeting the same mask can affect each other.

Each enabled instance repeats the Backlight lighting calculation in each relevant pass, plus one texture sample per shaded fragment when a texture is used. Each additional instance also adds a local shader keyword, which doubles the possible Backlight combinations before variant stripping. Disabled instances are excluded by their keyword, and the material optimizer can strip them using their own enable property. No extra render pass is added.

### HDR Tint Colors

Use `[ThryHDR]` for ordinary tint colors. It turns on the HDR color picker in Thry's inspectors without setting Unity's `HDR` shader property flag:

```hlsl
[ThryHDR] _MyTint ("Tint", Color) = (1, 1, 1, 1)
```

Adding this drawer to an existing ordinary `Color` property keeps its saved values, alpha, and gamma-to-linear conversion. Values above 1 are allowed and use that same conversion. Keep any existing brightness or intensity multipliers, since the drawer doesn't change any shader math.

Use Unity's `[HDR]` when a new property needs linear HDR values, such as an emission color.

:::warning
DO NOT remove existing `[HDR]` or `[Gamma]` attributes to switch to the tint picker. That would reinterpret existing materials and animation values.
:::

In 11.0 and newer, existing HDR properties keep their original flags, except Theme Colors 0–3. Those deliberately switch from `[HDR]` to `[ThryHDR]` to match ordinary tints, so saved non-white theme colors can render differently in Linear color space. Their stored values aren't migrated. Older shader versions, and other shaders that use ThryEditor, are unchanged.

## Shared Raymarching Data

:::info
The Raymarching Data module only exists in Poiyomi Pro. A Third Party module that depends on it fails to generate in the Toon shaders. See the [Third Party Limitations](/third-party/third-party.mdx#limitations).
:::

Anything that raymarches through the mesh needs the same two baked inputs: an SDF volume of the mesh, and its bind pose stored in the mesh UVs. Both come from one bake, so they live in their own module, `Poi_FeatureModules/Pro/Poi_Raymarching`. It owns the **SDF Volume & Bind Data** section under Raymarching, the **Bake SDF + Bind Data** button, and these properties: `_SDFTexture`, `_SDFPixelSize`, `_SDFLowerCorner`, `_SDFSize`, `_MinThickness`, `_BindDataMode`, the three bind UV slots, and `_WorldRecale`.

To use it from your own raymarching module:

1. Add `Poi Raymarching Data` to your `ModuleDependencies`.
2. Request the data from your keywords template, so shaders without your feature carry none of it:
   ```hlsl
   #ifdef MY_RAYMARCHING_KEYWORD
       #define POI_RAYMARCHING_DATA
   #endif
   ```

3. Add your enable property to the `//ifex` lines in that module's templates, so the optimizer can still strip the data from locked materials that use no raymarching feature at all.

You then get the following, guarded by `POI_RAYMARCHING_DATA`:

| Name | Description |
|------|-------------|
| `PoiGetModelThickness(startPos, marchDir)` | Distance from a point inside the mesh to where the ray exits, marched through the baked SDF |
| `PoiUseBindData(poiMesh)` | Whether to march in bind space. Forced on, or automatic when the mesh carries bind data |
| `poiMesh.bindPosition`, `poiMesh.bindNormal`, `poiMesh.bindTangent` | The bind pose at this fragment |

## Best Practices

1. **Always wrap code in feature guards** - Use `#ifdef` and `//ifex` to exclude unused code
2. **Use texture property guards** - Only declare textures when they might be used
3. **Follow naming conventions** - Consistent prefixes help organization
4. **Declare variables in correct sections** - Match passes where they're used
5. **Use appropriate queue values** - Lower values execute first
6. **Test with optimizer enabled** - Ensure guards work correctly
7. **Provide documentation links** - Use `button_help` for tutorials
8. **Prefix every property** - Start property names with your module's name (`_MyModule…`) so they can't collide with another module's
9. **Put numbers in `_EXPOSED`** - Floats, vectors and colors go in `<PASS>_PROPERTY_VARIABLES_EXPOSED`, textures and samplers in `<PASS>_PROPERTY_VARIABLES`. See [Variable Declarations](#variable-declarations)

## Troubleshooting

### Common Issues

1. **Module not appearing in shader**
   - Verify the module is added to the appropriate ModuleCollection
   - Check that the GUID references in the .asset file are correct
   - Ensure Unity has reimported the meta files
   - For a Third Party module, make sure it's outside the Poiyomi folder, and that it has been installed from the **Third Party** section of a material
   - Check your keywords for typos, since a misspelled keyword is skipped without an error

2. **Properties not showing in material**
   - Check `//ifex` conditions match property values
   - Verify `m_start_` and `m_end_` markers are properly paired
   - Ensure `reference_property` points to a valid toggle

3. **Shader compilation errors**
   - Check for missing `#endif` or `//endex` closures
   - Verify variable declarations are in the correct pass sections
   - Ensure texture samplers are properly guarded with `PROP_` checks

4. **Optimizer stripping needed code**
   - Use `isNotAnimated()` checks for animated properties
   - Verify `//ifex` conditions correctly reflect property states
   - Check that shader features use `shader_feature_local` for optimization

5. **Code running in wrong passes**
   - Verify keywords match the intended passes (BASE, ADD, SHADOW, etc.)
   - Check queue values don't conflict with other modules
   - Use pass-specific defines like `POI_PASS_BASE` for conditional code

### Debugging Tips

- Use the Debug module to visualize values
- Turn on the **DEBUG** section (`_DEBUGEnabled`) to access debug output
- Check the generated shader code in the Shaders folder after generation
- Test with optimizer both enabled and disabled

## Development Workflow

### Auto-Rebuild Shaders

When developing modules, enable automatic shader rebuilding to see changes immediately:

1. Go to `Poi -> Modular Shaders Generator`
2. Check the checkbox next to the shader(s) you want to auto-rebuild
3. The shader will now regenerate whenever you modify module files

The generator window shows all available shader variants with their source module definitions. You can also manually trigger rebuilds by clicking **Generate Shaders**.

For a module installed from **Third Party**, editing any of its files makes Third Party show an **Update** row marked "new changes". Click it to rebuild with your edits. See [The Development Loop](/third-party/third-party.mdx#the-development-loop).

### Shader Output Destinations

Each shader has configurable output settings:
- **Destination** - Output folder for generated shader files
- **Shader Name Match** - Filter which shaders get generated (StartsWith, Always, etc.)
- **Version Override** - Custom version number for the generated shader

## Adding Modules to Shaders

There are two ways a module ends up in a shader:

- **Third Party modules** are installed from the **Third Party** section of any Poiyomi material. No collection asset needs editing. See [Third Party](/third-party/third-party.mdx).
- **Core modules** are included via Module Collections. Add your module reference to the appropriate collection asset (e.g., `ModuleCollectionPro.asset`) or create a custom shader definition that includes your module.

## Shipping a Module

Export both files as a `.unitypackage`, plus your icon if you set one. Nothing else is needed: no folder requirements and no manifest. Importing it anywhere in a project makes it appear in the Third Party section of every Poiyomi material, ready to install.

To ship an update, export the same files again. When someone imports the newer version, Third Party shows an **Update** button that rebuilds with it. Bump `Version` so the button can show which version they're moving to.

See [Shipping A Custom Module](/third-party/third-party.mdx#shipping-a-custom-module) for what to leave out of the export, and why the `.meta` files matter.
